# flywheel 维护手册

flywheel 按个人持续维护的能力库运行。维护目标是让内容可发现、变化可追溯、版本可引用，
并让实际使用反馈进入下一次改进。维护者决定范围、接受变更和发布版本；按个人时间处理反馈，
不承诺固定响应时限或发布周期。

## 维护设施与职责

| 设施 | 解决的问题 |
| --- | --- |
| [README](../README.md) 与组件 README | 读者选择能力，进入对应介绍 |
| [Issue 表单](../.github/ISSUE_TEMPLATE/) 与 [PR 模板](../.github/PULL_REQUEST_TEMPLATE.md) | 收集可处理的反馈，记录变更依据、影响与验证 |
| 本手册 | 维护、贡献和发布流程，以及文末版本记录 |
| [仓库检查器](../scripts/check_repository.py) 与 CI | 自动发现结构、入口、引用和能力索引漂移 |
| [发布预检](../scripts/prepare_release.py) | 检查本地发布条件，预览发布说明 |

本文件是维护与发布流程的权威来源。组件的使用说明与能力资源留在组件内；迁入前的
通用化与隐私门禁沿用孵化仓约定。仓库检查不重复定义该门禁。

## 从反馈到变更

1. 使用者先搜索已有 Issue，再选择问题、需求或试用反馈表单。实际问题附能力、版本或
   commit、环境、复现步骤及预期与实际结果；需求说明场景和验收结果；试用反馈附任务、
   卡点及可检查的结果。公开材料移除凭据与私人信息。维护者自己的小改动可以直接记录在
   提交或 PR 中，不要求先创建 Issue。
2. 先判断是否属于已有能力或仓库维护范围。信息不足时一次说明所需复现条件；范围之外的
   请求解释原因后关闭。大功能先确认目标、边界和验收，再实施。
3. 接受的变更一次围绕一个目标，保留现有工作区修改。个人维护可直接提交到 `main`；
   外部贡献或需要讨论的变更通过开发分支与 PR 处理。PR 或提交说明
   记录问题、变化、影响、实际验证及未验证项；能力迁入或删除时同步更新根 README 索引。
   能力目录遵循 [结构约定](../AGENTS.md)，使用说明与资源保留在各自目录内。
4. 运行必要检查，由维护者确认变更符合目标、没有扩大范围，再按授权合入。关联 Issue
   以结果和对应提交或 PR 结束，留下可回查的依据。
5. 影响用户选择、使用方式或维护方式的变化记入本手册的 `Unreleased`；纯排版
   和错别字修改通常不单独记录。收齐一批值得使用者关注的变化后发布。

## 本地检查与 CI

维护脚本使用 Python 3.11+ 标准库。在仓库根目录运行：

```bash
python -B scripts/check_repository.py
python -B -m unittest discover -s tests -v
```

默认检查当前工作区，包括尚未跟踪的能力。待发布文件检查使用：

```bash
python -B scripts/check_repository.py --tracked
```

`--tracked` 以 Git index 中的文件作为可交付范围，仍读取当前工作区内容。README 指向本地
存在但未跟踪的目录时会失败。它用于发现遗漏，不能代替发布时的干净提交检查。

GitHub 的 `Repository check` 在 push、PR 和手动触发时，于 Linux、Windows 的 Python 3.11
环境执行待发布文件检查与维护脚本测试；CI 与发布预检都要求实际执行至少一个测试，
防止空测试集合被视为通过。检查器同时要求核心维护脚本、测试、工作流与模板纳入交付范围。
配置随提交推送后生效；以目标提交的实际运行结果
判断通过，不能仅凭有工作流文件就宣称 CI 已通过。

结构检查只能证明文件、入口、引用和索引满足约束。能力执行规则的实质变化需要相应的代表
任务证据；脚本行为变化需要实际输入与错误路径验证。涉及外部平台的在线可用性单独记录，
不由本仓库的结构 CI 推断。本次维护设施的测试也不执行现有下载或抓取工具。

## 版本策略

整个仓库使用一套 `v0.MINOR.PATCH` 版本。`main` 保存最新内容，tag 固定已发布快照，
Release 对应 `main` 上的一个提交。组件仍可按目录独立取用，不单独编号。

首发 `v0.1.0` 包含两个独立 Skill（`wx-fetch`、`dy-video`）与 `development` 套件。
后续发布按下表选择版本；同时出现多类变化时，取较大的升级级别。

| 变化 | 处理 |
| --- | --- |
| 首次形成可引用的公开快照 | `v0.1.0` |
| 纠错或补充，现有使用方式保持兼容 | 增加 PATCH，例如 `v0.1.1` |
| 新增或移除能力，明显改变接口、执行流程或依赖 | 增加 MINOR，例如 `v0.2.0`，PATCH 归零 |
| 纯排版、错别字或内部整理 | 正常提交，通常不单独发布 |

0.x 阶段仍须说明不兼容变化、受影响用法和迁移办法。已有 tag 与 Release 不覆盖重写；
已发布内容需要修正时，发布后续版本并说明变化。是否进入 1.0 取决于使用契约和维护范围
是否稳定，不以时间或 Star 数决定。

## 发布步骤

1. 整理 `Unreleased`，只保留本次实际完成且影响使用者的变化；相关组件介绍、索引、
   验证证据和兼容说明保持一致。选择版本，先查看草稿：

   ```bash
   python -B scripts/prepare_release.py v0.1.0 --preview
   ```

   预览允许未提交变化，并列出阻塞；它不会创建 tag、修改更新记录或发布 Release。
2. 将本次变更整理到本手册末尾对应的版本段，格式为
   `## [v0.1.0] - YYYY-MM-DD`，日期使用实际发布日；保留 `Unreleased` 供后续维护。
3. 按授权提交并合入 `main`。确认目标提交的 CI 通过，关联的实际行为证据可查看；
   本地工作区与 index 干净，再执行：

   ```bash
   python -B scripts/prepare_release.py v0.1.0
   ```

   预检检查本地分支、工作区、同名本地 tag、版本说明、待发布文件和维护脚本测试。
   成功只表示这些本地条件通过。
4. 在 GitHub 核对远端 `main` 的目标提交、同名 tag/Release 和 CI 结果。公开发布属于
   外部写入，执行前取得发布授权；本地预检不查询远端，也不自动创建或推送 tag。
5. 从目标提交创建 tag 与 Release。说明包含变化、受影响能力、验证范围、已知限制和
   必要迁移方式。GitHub 自动生成的提交列表只能补充用户说明。
6. 检查 Release 链接、源码 ZIP 下载、该版本的能力入口和 Issue 表单是否可用。
   发布后收到问题，关联版本进入新的 Issue 和 `Unreleased`。版本号、tag 和 Release
   由维护者统一处理。

## 运行节奏与反馈优化

按可用时间集中处理 Issue，优先修复阻断使用的问题，再考虑增强。接受的反馈关联到
提交或 PR，用户可见变化进入 `Unreleased`，积累值得关注的变化后按版本规则发布。
没有值得发布的变化时不为保持频率发布，不承诺尚未接受的路线图。

## [v0.1.0] - 2026-10-03

### 能力范围

- `development`：AI 辅助开发 Skill 套件，覆盖业务理解、技术设计、测试设计、开发、问题处理与复盘。
- `wx-fetch`：微信公众号文章抓取、正文解析与本地缓存。
- `dy-video`：抖音视频与音频解析下载，并支持配合 Agent 多模态能力提取台词。

### 新增

- 首个统一版本快照，包含两个独立 Skill 和 `development` 套件。
- 集中的维护手册，包含反馈处理、贡献、版本规则与发布流程。
- 实际问题、新需求和试用反馈的 Issue 表单，以及说明影响与验证的 PR 模板。
- 仓库结构、Skill 入口、相对引用和能力索引检查，配套维护脚本回归测试与双平台 CI。
- 只读发布预检与发布说明预览，用于检查本地发布条件并展示阻塞。

### 调整

- 根 README 改为面向使用者的能力定位，索引指向可独立取用的组件目录。
- 根目录只保留 README 与 AGENTS 两份 Markdown，维护流程和版本记录集中在 `docs/maintenance.md`。

### 验证与限制

- 结构检查和维护脚本测试覆盖目录、入口、声明的本地引用、能力索引与发布预检行为。
- 该检查范围不包含能力的实际执行效果或微信、抖音等外部平台的持续可用性。
- 使用方式、依赖和个性化条件以该版本内各组件 README 与 SKILL.md 为准；本版本不提供独立安装器。
